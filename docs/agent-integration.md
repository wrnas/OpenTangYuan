# Agent Integration Guide

OpenTangYuan can serve as a local execution runtime for Coze, Dify, GPTs, custom agents, or ordinary clients.

The external agent is responsible for:

- understanding the user's request;
- querying the capabilities available in the local environment;
- selecting a workflow or built-in skill;
- collecting or asking for required parameters;
- constructing single-step or multi-step requests.

OpenTangYuan is responsible for:

- validating and executing requests;
- accessing local and enterprise resources;
- resolving workflow template variables;
- managing step context;
- returning structured results.

## 1. Recommended Call Flow

```text
User request
   ↓
GetSkillListForAI
   ↓
Is there a matching workflow?
   ├─ Yes → GetSkillAction
   └─ No  → GetBuiltinSkillDetail
   ↓
Validate required parameters
   ↓
ExecuteSkill / ExecuteSkillForCoze
   ↓
Present the result and stop
```

## 2. Recommended Tool Definitions

Most agent platforms only need the following core tools:

| Tool | Endpoint | Purpose |
|---|---|---|
| `GetSkillListForAI` | `/api/Skills/GetSkillListForAI` | Retrieve summaries of workflows and built-in skills. |
| `GetSkillAction` | `/api/Skills/GetSkillAction` | Retrieve the steps of a saved workflow. |
| `GetBuiltinSkillDetail` | `/api/Skills/GetBuiltinSkillDetail` | Retrieve the actions and parameters of a built-in skill. |
| `ExecuteSkill` | `/api/Skills/ExecuteSkill` | Execute a built-in skill, database workflow, or temporary workflow. |
| `ExecuteSkillForCoze` | `/api/Skills/ExecuteSkillForCoze` | Execute through a serialized string parameter for constrained platforms. |

The agent does not need to store every built-in skill parameter permanently in its system prompt. It should read the real definitions exposed by the current deployment through the capability-discovery APIs.

## 3. Decision Rules

1. Query the capability catalog when a new task arrives.
2. If a matching workflow exists, retrieve its details first.
3. If no matching workflow exists, retrieve the relevant built-in skill details.
4. Use only capability names and parameter definitions returned by the APIs.
5. Ask the user when required parameters are missing.
6. Do not guess email addresses, recipients, file names, local paths, or credentials.
7. After execution, decide whether to stop based on the returned result.

## 4. Stop Rules

### Ordinary Success

When the user's goal has been completed, stop immediately and do not call additional skills.

### List Queries

When an email search, file search, or similar operation returns a list:

1. present the list to the user;
2. stop execution;
3. continue only when the user explicitly asks to inspect an item, download an attachment, or perform another action.

### Side-Effect Operations

The following operations must stop immediately after success:

- sending or replying to email;
- copying, moving, renaming, or deleting files;
- downloading attachments;
- marking email as read;
- saving files;
- printing;
- launching a local program;
- sending enterprise messages.

Do not repeat a successful operation merely because a natural-language confirmation was not returned.

### Failure Retry

A failed skill may be retried once when the parameters have been clearly corrected. If the second attempt also fails, report the error and stop.

## 5. Parameter Format

`ExecuteSkill` uses only these top-level fields:

```text
SkillCode
Arguments
Steps
```

When no arguments are required, pass:

```json
{
  "Arguments": {}
}
```

Do not add top-level fields that are not defined by the API.

### Single-Step Example

```json
{
  "SkillCode": "wechat_task",
  "Arguments": {
    "action": "text",
    "content": "The task is complete"
  }
}
```

### Temporary Workflow Example

```json
{
  "SkillCode": "temp_task",
  "Arguments": {},
  "Steps": [
    {
      "Action": "browser_task",
      "Args": {
        "actions": [
          {
            "type": "goto",
            "url": "https://example.com"
          },
          {
            "type": "get_text",
            "selector": "body"
          }
        ]
      }
    },
    {
      "Action": "wechat_task",
      "Args": {
        "action": "text",
        "content": "The task is complete"
      }
    }
  ]
}
```

## 6. Workflow Context

Later steps should reference context values generated by the runtime rather than guessing intermediate results:

```text
{{step0}}
{{step0.data.path}}
{{step0.data.firstPath}}
{{step1.result}}
```

The agent should select field paths from the actual response of the preceding step.

## 7. Email Rules

Recommended flow:

```text
search → present the list and stop
user selects an item → read / download_attachments / reply / mark_read / save_eml
```

When sending email:

- use `attachments` for ordinary file attachments;
- use `insertImagePaths` for images embedded in the message body;
- stop immediately after the message has been sent successfully.

## 8. Screenshot Rules

- For web-page screenshots, use `browser_task`.
- For the local desktop or a local application window, use `open_task` with `screenshot_task`.
- Do not mix the two approaches unless the task genuinely requires both web and desktop capture.

## 9. Deployment-Specific Workflows

Some installations may include custom workflows for office-system messages, internal approvals, or other organization-specific operations. These capabilities are not guaranteed to exist in every deployment.

Agents should use `GetSkillListForAI` to determine which workflows are available in the current instance and should not hard-code deployment-specific `SkillCode` values.

## 10. Coze Integration

Platforms such as Coze can use `ExecuteSkillForCoze` to pass serialized JSON. See the [Coze System Prompt](coze-system-prompt.md) and adapt it to the deployed endpoint, authentication scheme, and capability catalog.

## 11. Security Requirements

- Parameters generated by an external agent must be validated by the local runtime.
- Agents must not bypass allowlists or permission policies.
- Do not place real credentials in prompts.
- Do not send internal-system data to an unauthorized external service.
- Add human confirmation for high-risk tasks.
- Use strict stop rules for side-effect operations.
